# Задачи для владельца predict-service

Контекст: демонстрационный стенд использует синтетические HR-данные. Результаты не относятся к реальным сотрудникам или фактическому внедрению в Т2.

## P0 — блокирует надёжный API-прогон

1. Исправить прогноз с `fh=1`.
   - Сейчас `squeeze().tolist()` возвращает число, после чего код обращается к нему по индексу.
   - Критерий готовности: запрос с `fh=1` возвращает ровно одну строку прогноза без `TypeError`; добавить регрессионный тест.

2. Исправить определение месячной частоты.
   - Проверка `M` выполняется раньше `MS`, поэтому ветка `MS` недостижима и даты начала месяца преобразуются некорректно.
   - Для событийных рядов (например, увольнения по месяцам) пропущенный месяц нельзя безусловно заполнять предыдущим значением; политика должна задаваться явно, обычно `0` для количества событий.
   - Критерий готовности: отдельные тесты для `MS`, `M/ME` и пропущенного месяца.

3. Добавить авторизацию CSV callback.
   - Сейчас callback к `/csv/schema` и `/csv/query` не имеет авторизации.
   - Согласовать общий секрет или короткоживущий service token; predict-service должен передавать его в заголовке каждого callback, backend — проверять.
   - Не писать токен в логи и тексты ошибок. Закрыть прямой анонимный доступ тестом с `401/403` и успешный доступ с валидным токеном.

4. Зафиксировать сетевой контракт callback.
   - `BACKEND_PUBLIC_API_URL=http://localhost:...` на удалённом predict-сервере указывает на сам predict-сервер, а обычный SSH `-L` не создаёт обратный маршрут.
   - Поддержать реально доступный URL (service DNS/reverse proxy или явно документированный reverse tunnel) и возвращать понятную ошибку недоступности callback.

## P1 — корректность выбора и подготовки ряда

5. Заменить regex-проверку SQL на разбор SQL.
   - Regex сейчас видит запрещённые слова внутри строковых литералов, например значения `COPY` или `GRANT`.
   - Минимальный вариант: парсер DuckDB (`extract_statements`) и ровно один statement типа `SELECT`; альтернативно — `sqlglot` с явным dialect.
   - Учесть, что read-only `SELECT` с table functions может читать внешние файлы: разрешить только ожидаемые таблицы/источники.

6. Валидировать смысл временного ряда, а не только алиасы `dt, y`.
   - Для HR-сценария нужен агрегат увольнений по `termination_date`, а не произвольная дата снимка или фильтр по несуществующему признаку.
   - Перед прогнозом проверять типы, сортировку, уникальность периода, регулярность частоты, отсутствие будущих строк и понятное описание выбранной метрики.
   - Возвращать в ответе фактически выполненный SQL и краткое описание ряда для аудита демо.

7. Реализовать обещанный выбор таблицы для multi-file CSV.
   - Сейчас используется только `table_name`, а список `table_names` из schema callback игнорируется.
   - Критерий готовности: тест с двумя CSV-таблицами, где модель выбирает вторую и запрос выполняется именно по ней.

8. Нормализовать контракт ошибок и пустых результатов.
   - Пустой прогноз не должен возвращаться как успешный результат.
   - Использовать стабильные коды ошибок для: callback недоступен, SQL отклонён, ряд пуст, ряд слишком короткий, частота не определена, модель не построила прогноз.

9. Сделать readiness-проверку интеграции.
   - Простого `/health` predict-сервиса недостаточно: readiness должна проверять доступность callback и минимальный запрос к тестовому источнику.
   - UI может показывать «доступно» только после такой проверки, а не только по наличию URL в конфигурации.

## Рекомендуемые готовые компоненты

- DuckDB parser или `sqlglot` вместо собственного regex-анализатора SQL.
- Pydantic-модели для входного и выходного API-контракта.
- `pandas.infer_freq`/явная частота с отдельной политикой заполнения пропусков вместо эвристики по префиксу строки.
- Стандартная service-to-service авторизация через reverse proxy/API gateway, если он уже есть в контуре; не изобретать отдельный протокол.
